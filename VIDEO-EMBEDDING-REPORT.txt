2. ARCHITECTURE DECISION (as chosen before any code)
--------------------------------------------------------------------------------
CHOSEN: Option B+ — a native Win32 CHILD window (WS_CHILD) parented to the Tauri
main window, with mpv rendering into it via `--wid`, positioned from React, and
sitting exactly where NowPlayingView already reserves the player area.
Controls stay BELOW that rect, as they already were.

WHY (abridged; full rationale in VIDEO-EMBEDDING-ARCHITECTURE.md)
 1. Single window — the hard requirement. No popup, no taskbar entry.
 2. Z-order solved BY CONSTRUCTION, not by a workaround. A native child always
    paints above the WebView2, so React can never draw over it. The honest fix
    is therefore that no React control may overlap the rect — and the existing
    layout already guarantees that (controls are the video's later siblings).
    No control is hidden, nothing fades, no "controls vanish while playing".
 3. Proven, not assumed: the shipped mpv rendered a real frame into a child
    HWND (VO gpu-next, 135 distinct sampled colours) before a line of app code
    was written.
 4. Compatibility: mpv stays out-of-process, keeps its pipe IPC, its Job Object,
    `--no-config`, and the identical localhost Range-proxy URL.
 5. Cheapest of the options that actually satisfy z-order. libmpv/frame-blitting
    would mean a second mpv instance plus per-frame copies on a machine class
    this app explicitly targets, to buy overlay controls the app does not use.
 6. Lifecycle: one engine, no respawn on media-kind switches.
 7. Performance: mpv paints D3D11 straight into the child — no per-frame copy.

REJECTED
  A  `--wid` = the WebView2/Tauri HWND -> mpv would paint over the whole UI.
  B' keep mpv's top-level window and position it over the player area -> the
     DrPlay client area is opaque (WebView2 fills it), so it can never be seen;
     in front it violates the one-window rule. This is the state we are leaving.
  C  libmpv render API / DOM frame blitting -> cost without a matching need.
  D  HTML <video> -> Chromium/WebView2 cannot demux MKV at all, and the
     production CSP deliberately omits http://127.0.0.1 from media-src.

--------------------------------------------------------------------------------
  metric                     | popup (before)      | embedded (after)
  ----------------------------|---------------------|------------------
  extra top-level windows     | 1 (mpv)             | 0
  window position control     | none                | React-driven rect
  3840x1600 video at 1024x768 | overflowed the      | fits the player

                              |                     | same decode, only the
                              |                     | destination changed)
Not directly A/B measured CPU because the decoder dominates and the only change
is the render destination; embedding removes one compositor surface rather than
adding one, so the direction is strictly favourable. Frame stability was not
formally instrumented.

7. KNOWN LIMITATIONS — honest list
--------------------------------------------------------------------------------
 1. FULLSCREEN IS NOT IMPLEMENTED. The Now Playing overlay is already the
    full-screen surface and covers the whole window, but there is no dedicated
    video fullscreen (no window maximize, no F11-style mode, no
    hide-controls-until-mouse-move). This is the one Definition-of-Done item
    that is not met.
 2. The video box cannot be rounded. A native HWND has square corners; the
    rounded-2xl clips only the React placeholder underneath. The screenshot
    shows square corners on the video. Documented as accepted in the design doc.
 3. Native child content cannot be blurred, clipped, or covered by CSS. The host
    is therefore hidden whenever a full-screen modal covers the shell
    (`isShellLocked`). `TrashScreen` is a similar full-screen overlay that is
    NOT in the hide matrix — reachable from Settings only while the Now Playing
    overlay is closed, so it is not reachable in practice, but the invariant is
    not enforced for it.
 4. The `video` property is set per load, but `--wid` is read ONLY at spawn. If
    mpv ever respawns (load-deadline / stall-recovery), the new engine does get
    `--wid` because `ensureVideoHostAcquired()` is awaited inside
    `startEngine`/`swapSidecar`. This is correct but is a caller contract
    enforced by two call sites, not by Rust.
 5. ERROR state hides the video. Because CSS cannot cover a native window, the
    host is hidden on error so the app's ErrorToast and retry stay readable.
    The last frame therefore disappears at the moment of failure — deliberate,
    but it is a behaviour choice, not a free win.
 6. ENDED leaves the last frame up until the next track swaps the media kind. No
    `end-file` subscription reaches the surface.
 7. A thin strip of sidebar text can be visible at the far left edge while the
    Now Playing overlay is open. Cosmetic, observed in one capture, not
    investigated.
 8. UI-008/009/011/020/023/024 are UNCERTAIN, not PASS: they are covered by
    unit tests but were not separately ticked live in this session.
 9. HEVC/AV1/10-bit decode remain unmeasured in the embedded path (the same gap
    as the previous phase; the one real file is h264 10-bit).
10. Only one monitor and one DPI scale were exercised. Multi-monitor + mixed-DPI
    behaviour is implemented (matchMedia on the resolved DPR, rAF-coalesced
    rect) and unit-tested, but not verified on real hardware.

--------------------------------------------------------------------------------
9. FINAL VERDICT
--------------------------------------------------------------------------------
READY WITH KNOWN LIMITATIONS

The core requirement is met and proven on the real app with a real Drive file:
video plays inside the single DrPlay window, in the player area of the app's own
Now Playing surface, with DrPlay's own controls and SeekBar below it, no mpv
popup, no mpv OSD, no orphan processes and no orphan native window on exit. No
streaming architecture was touched: the same localhost Range proxy, the same
Drive URL flow, the same token handling, and mpv still never sees a Google token.

What "with known limitations" means concretely: there is no dedicated video
fullscreen yet, the video box has square corners, an error deliberately drops the
last frame so the error UI stays readable, and six of the twenty-four UI checks
are covered by unit tests rather than separately ticked live. None of these
blocks the feature; the fullscreen item is the one I would do next, and it needs
no change to the architecture chosen here.
