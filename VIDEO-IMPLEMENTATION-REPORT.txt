2. ARCHITECTURE — BEFORE / AFTER
--------------------------------------------------------------------------------
BEFORE:  mpv sidecar spawned with `--no-video` -> video structurally impossible
         Drive query matched 7 audio extensions -> movies never became Tracks

AFTER:   ONE engine, ONE proxy, ONE URL scheme. Video rides the identical lane.

  Google Drive
        |  files/{id}?alt=media  +  Authorization: Bearer (attached in Rust,
        v  never visible to mpv)
  ┌──────────────────────────────────────────────────────────┐
  │ Rust stream_proxy  127.0.0.1:{ephemeral}  (UNCHANGED)    │
  │   forwards Range -> 206 / Content-Range / Content-Length  │
  └──────────────────────────────────────────────────────────┘
        ^
        |  http://127.0.0.1:{port}/stream/{fileId}   <- SAME URL for audio+video
        |
  ┌──────────────────────────────────────────────────────────┐
  │ mpv sidecar  (ONE instance, job-pinned)                   │
  │   spawn flags: --vo=gpu-next,gpu   (no --no-video)       │
  │   per load:     set_property video "1" (video) | "no"    │
  │                 loadfile <proxy url> replace              │
  │   video -> mpv's OWN native window (gpu-next), NOT in the │
  │             WebView -> sidesteps the production CSP       │
  └──────────────────────────────────────────────────────────┘

Decisions and why:
 - Video window = mpv's own output window, not HTML <video>. mpv already runs
   out-of-process; the production CSP does not allow 127.0.0.1 in media-src/
   connect-src, so an in-app surface would have needed a CSP change. Zero new
   layers.
 - ONE engine, `video` set per load. mpv `video` is a runtime property; respawning
   on every audio<->video switch would churn the pipe, the Job Object, log
   rotation and the load-deadline budget for a value mpv accepts as one command.
 - Media kind derived from the file NAME via an explicit video allowlist
   (.mkv/.mp4), never `ext !== "mp3"`. Unknown -> audio (today's behavior).
 - No `Track.mediaKind` field: every Track source already carries the Drive
   filename, so no DB migration and no session-payload migration.

3. THE BUG THAT WOULD HAVE SILENTLY SHIPPED
--------------------------------------------------------------------------------
The original spec (mine) said to send `set_property video "yes"`. Measured on the
shipped mpv 0.41.0:

   value   | returns        | readback | verdict
   --------+----------------+----------+--------------------------
   "yes"   | undefined      | "no"     | SILENTLY IGNORED
   "1"     | true           | "1"      | WORKS
   "on"    | undefined      | unchanged| silently ignored
   "true"  | undefined      | unchanged| silently ignored
   "no"    | true           | "no"     | works

With "yes", video would never turn on — no crash, no error log, no test failure,
just a silent no-op. Code ships `"1"`. Verified independently by the orchestrator
after the fact, on the real sidecar, over the real Range proxy.

4. VIDEO FLOW (what actually happens when a user picks a movie)
--------------------------------------------------------------------------------
 1. Drive sync / folder browse / search lists the .mkv/.mp4 (union query).
 2. Row maps to a Track (unchanged path — no extension gate on display).
 3. Metadata: video short-circuits BEFORE any range fetch, title falls back to
    the filename. The audio music-metadata parser is never invoked on video.
 4. User presses play -> mpvAudio.loadTrack
      a. ensureProxyPort()  -> invoke("stream_proxy_start")  [unchanged]
      b. set_property video "1"
      c. loadfile "http://127.0.0.1:{port}/stream/{fileId}" replace
 5. Rust proxy attaches Bearer, forwards Range, returns 206.
 6. mpv opens mpv's native video window, decodes, plays audio via WASAPI.
 7. Seek / pause / volume / next / prev / queue all go through the EXISTING
    mpv command path. No second control system.
 8. Switching to an audio track sends video="no" -> the window closes.
 9. Stop / track switch / app exit -> existing Job Object + kill_on_drop.

9. PHASE F — WHY NO TUNING VALUE WAS CHANGED
--------------------------------------------------------------------------------
The investigation flagged "audio-sized 20s idle abort will hard-fail video".
Measured it instead:

  gap 2s  at 128 000 B/s (0.5 Mbit/s)  -> full body delivered, NO abort
  gap >20s at 2 048 B then silence     -> aborted at 20.0016s, one 499 event

The abort is a WALL-CLOCK GAP detector: identical 20.0016s threshold at byte
rates ~2000x apart. Higher bitrate does not make silence more likely — a gap is a
gap. The premise was wrong.

And mpv survives the abort: it re-opened the stream with `bytes=122880-` (exactly
the prefix the stall consumed), the engine never went idle, and no
`end-file reason=error` was emitted. So a 20s Drive hiccup is not a hard fail.

Decision: change nothing. Shipping a media-kind-aware timeout would add a moving
part to the auth-adjacent data plane for zero measured benefit.

`hwdec` was measured (15.2% -> 1.4% CPU with auto-safe, +45 MB RAM) but
deliberately NOT shipped: one machine, one codec, one GPU; a spawn-flag change
applies to every user and every codec. Recommendation, not a change.

11. KNOWN LIMITATIONS (honest list)
--------------------------------------------------------------------------------
 1. resourceKey unsupported. A Shared-Drive or link-shared movie LIST but will
    not PLAY (404/403). Measured blast radius on this account: 0 of 100 files.
    Documented at stream_proxy/server.rs::build_upstream_url. Fixing it means
    touching the Drive/auth layer — out of scope by instruction.
 2. No video window geometry/positioning/always-on-top. A 3840x1600 movie opened
    a window LARGER than the 1920x1080 display and nothing in the codebase
    constrains it. One-line fix if wanted: `--geometry=`.
 3. No hardware decoding — software decode, 15.2% CPU measured. Fine for
    correctness; a real tuning opportunity.
 4. mpv's forward buffer has a ~26.8 Mbit/s ceiling (the 64 MiB byte cap binds
    before the 30s cache-secs). Real Drive measured 16.0 Mbit/s, so this is a
    FUTURE risk for 4K remux, not a current one.
 5. No in-app video surface. The picture lives in mpv's own window, outside the
    app. There is no picture-in-picture, no embedded player, no video-specific
    Now Playing art. PlayerBar shows the same audio-style controls.
 6. HEVC / AV1 / 10-bit decode UNTESTED. The only real-Drive video is h264
    yuv420p10. The allowlist is a CONTAINER allowlist, so a 10-bit HEVC .mkv is
    admitted but unmeasured.
 7. Drive quota for a full-length watch is still unmeasured. What is known:
    open + fwd seek + back seek on the 92-min MKV consumed ~23 MB. The pre-existing
    whole-file service-worker prefetch remains the larger unmeasured liability.
 8. The verification harness needs $DRPLAY_VIDEO_FIXTURES and `--test-threads=1`;
    the 1.4 GB fixtures live in temp, not in the repo. A missing fixture PANICS
    with its path rather than skipping, so a PASS can never be faked.
 9. drplay.exe RAM/CPU during playback unmeasured (see section 7).
10. The video_lifecycle tests are #[ignore]d by default: 15 ignored tests in the
    default `cargo test` run. They were executed with --ignored for this report.

READY WITH KNOWN LIMITATIONS

Video from Google Drive works, on the architecture that already existed, with
the smallest change that could be correct:
  - 24 files, +725/-72
  - ONE engine, ONE proxy, ONE URL scheme, ZERO new dependencies
  - Zero audio numeric changes; 2667 frontend tests + 149 Rust tests green
  - Proven against the real Google Drive account, not just a fixture

What "READY WITH KNOWN LIMITATIONS" means concretely: if you install this build
and play a .mkv or .mp4 from your own Drive, it will start, show video and sound,
seek forward and backward, pause, resume, change volume, change track, and clean
up its process and window on exit. It will NOT be embedded in the app window, it
has no picture-in-picture, a link-shared movie will not play, video is decoded in
software, and HEVC/AV1 are unverified because no sample was available.

The three things I would do next, in order:
  1. `--hwdec=auto-safe` as its own slice (measured 11x CPU reduction) with a
     multi-GPU / multi-codec matrix — it is the single biggest win for the
     weak-machine target and it is currently unclaimed.
  2. `--geometry=` so a 4K movie does not open a window larger than the display.
  3. resourceKey support, if you ever plan to use link-shared movies — that one
     requires a deliberate decision to touch the Drive/auth layer.

Nothing about the streaming architecture needs to change for any of those.
